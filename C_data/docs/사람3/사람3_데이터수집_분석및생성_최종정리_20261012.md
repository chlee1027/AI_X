# 사람3 데이터 수집·출처 편향·분리 및 생성 최종 정리

정리일: 2026-10-12  
주제: 공공사이트 불법 광고 탐지  
담당 범위: OFFSCREEN(화면에서 숨겨진 홍보 요소) 데이터

이 문서는 수집 방법 별도 정리와 출처 편향·생성 기준 문서를 통합했다. 사람3의 승인 원문 100개와 기존 CSS 동작 확인용 샘플, 추가 합성 데이터 112개를 구분해 설명한다. 사람1·사람2 자료는 포함되지 않았다. 완료한 작업, 보존된 검증 기록, 아직 시행하지 않은 제안을 구별했으며 이번 통합 과정에서 데이터를 새로 생성하거나 브라우저 검증을 실행하지 않았다.

## 1. 데이터 구성과 현재 상태

|---|---:|---|

원문 100개는 개별 광고 요소의 수이며 서로 다른 페이지 100개를 뜻하지 않는다. 기존 fixture와 원문은 파생 관계가 있으므로 개수를 합산해 독립 수집량으로 보고하면 안 된다. 원문과 기존 시험용 샘플의 구분은 완료했지만 독립적인 실제 train/test 분리는 확인되지 않았다. 추가 합성 데이터는 학습 보강 84개와 합성 validation 28개로 배정했으며 실제 test 데이터는 없다.

기술적 숨김 홍보 판정과 법적 불법성 판정은 구분한다. 이 자료의 양성 라벨은 OFFSCREEN 숨김 홍보 탐지를 위한 것이며 법적 불법성을 확정하는 표시가 아니다.

## 3. 수집 공정성과 편향을 줄인 방법

여기서 공정성은 출처 집중·중복·유형 편향·판정 일관성·근거 투명성을 뜻한다. 인구집단별 모델 공정성이나 실제 성능을 평가한 결과는 아니다.

- 출처 사이트 전체 페이지를 합쳐 최대 10개로 제한했다. Stack Overflow/Stack Exchange는 하나의 계열로, Sucuri도 하나의 계열로 계산했다. 원문 100개 기준 단일 계열 비중은 최대 10%다.
- 숨김 기법별 할당을 적용했다: font-size 0~1px·음수 left·display:none 45개, visibility:hidden 15개, clip/clip-path 15개, text-indent 10개, transform/문서 밖 좌표 15개. 흔한 기법만 모으지 않고 다섯 유형을 확보했다.
- 동일 목적지·브랜드·의심 도메인 계열을 보수적으로 중복 처리하고 사람의 중복 판정을 반영했다. 이는 문구가 모두 고유하다는 뜻은 아니다. 원문 100개의 정확히 다른 evidence_text는 93개다.
- 일반 UI, 같은 광고가 이미지나 본문에 보이는 사례, 접근성 대체 문구, JavaScript 실행 후 정상적으로 드러나는 광고, 일반 캐러셀 등을 양성으로 세지 않도록 수집 기준에 명시했다.
- 최종 사람 검수 102개 중 원문 100개만 유형별 개수에 포함했고 참고 2개는 제외했다. 원문 부족을 자체 생성 변형으로 채우지 않았다.
- 현재 페이지 원문 52개와 과거 피해 코드 공개 사본 48개를 구분했다. 원문 HTML/CSS, 출처, 수집 해시, 사람 검수와 자동 관찰 기록을 보존했다.

## 5. 중요도 판단과 보완 우선순위 제안

빈도와 중요도를 따로 관리한다. 이미 많이 수집한 유형을 자동으로 중요한 유형으로 보는 대신, '공공서비스에서 실패했을 때의 영향'과 '학습에 필요한 정보'를 먼저 본다.

제안 점수는 `P = 0.35R + 0.25G + 0.25F + 0.15E`다. 각 요소는 1~5점이며 현 단계의 아이디어다. 검증된 통계 모형이나 법적 위험 점수가 아니다.

| 요소 | 판단 질문 | 5점 예시 |
|---|---|---|
| R: 공공서비스 영향 | 기관 신뢰를 빌려 이용자를 오인시키거나 민원·지원금·입찰 흐름에 영향을 줄 수 있는가? | 지원금 사칭 유료 안내, 입찰 선정 보장 홍보 |
| G: 확보 공백 | 실제 공공사이트·정상 UI·새 캠페인·복합 문맥 중 부족한 부분인가? | 미확보한 공공사이트 게시판의 새 원문 |
| F: 혼동 가능성 | 숨김 CSS가 같아도 정상 기능인지 광고인지 구별하기 어려운가? | 접근성 문구·보안 경고·숨김 광고가 같은 기법을 사용 |
| E: 근거 신뢰도 | 전체 페이지·스타일·목적지·가시성·사람 검수가 함께 있는가? | 현재 페이지의 CSS와 실제 화면 및 검수 기록 확보 |

예시로 '정상 스크린리더 안내 음성 사례'에 R=3/G=5/F=5/E=5를 부여하면 4.30점이다. '지원금 사칭 문맥의 새 실제 숨김 홍보'를 모두 5점으로 평가하면 5.00점이다. 반대로 동일 출처·동일 캠페인의 유사 광고 추가 사례를 R=3/G=1/F=2/E=4로 평가하면 2.40점이다. 숫자는 설명용 가정이며 실제 사례별로 담당자가 근거와 함께 확정해야 한다. 합성 사례는 근거 신뢰도 E에서 실제 피해 증거의 높은 점수를 받을 수 없다.

학습 시에는 출처·캠페인 그룹 내 표본 수 n에 대해 `w = 1/√n`을 시작점으로 검토할 수 있다. 전체 평균 1로 정규화하고 0.5~2.0 범위로 제한해 희소 그룹의 불확실한 라벨이 과도한 영향을 주지 않게 한다. 이는 아직 적용하지 않은 제안이다. 중요도 P를 곧바로 학습 가중치로 곱하면 임의의 판단이 성능을 왜곡할 수 있어, P는 추가 수집·검수 우선순위에 먼저 사용한다.

평가에서는 출처별 평균 성능과 전체 표본 기준 성능을 함께 보고한다. 희소 유형·정상 UI·공공 문맥의 오류를 별도로 보며, 합성 평가 성능과 실제 사이트 평가 성능을 합치지 않는다. 모델 오류가 많이 나는 그룹을 다음 수집 대상으로 삼는 방식도 가능하다.

## 6. 기존 원문과 시험용 샘플의 train/test 구분

### 확인된 상태

**원문과 시험용 샘플의 구분은 완료했지만, 머신러닝 train/test를 철저히 분리했다는 증거는 없다.** 최종 패키지에 train/test 할당 목록, 분할 비율, 분할 seed, 사이트별 그룹 배정, 학습 실행 기록은 확인되지 않는다. 여기서 “시험용”은 CSS 동작을 확인하는 fixture이며 독립적인 모델 평가용 test set이라는 뜻이 아니다.

| 묶음 | 개수·ID | 용도 |
|---|---|---|
| 자체 제작 양성 fixture | 100개, OF-001~OF-100 | 승인 원문 문구에 라이브러리 CSS 또는 파생 변형을 적용한 동작 확인 |
| 가시 대조군 | 7개, OF-101~OF-107 | 글자가 보이는 정상 동작 확인 |
| 실제 원문 발췌 | 100개, OF-108~OF-207 | 수집 당시 HTML/CSS와 출처 근거 보존 |
| 참고 사례 | 2개 | 유형별 원문 개수와 양성 fixture에서 제외 |

원문과 양성 fixture는 동일한 26개 출처 URL을 사용한다. fixture 100개 중 98개는 원문의 source와 evidence_text 조합에 정확히 일치한다. 나머지 2개의 불일치는 검증 기록상 원문 문자열 수정에 해당하므로 독립적으로 새로 수집한 test 데이터로 볼 수 없다. ID와 HTML/CSS가 달라도 출처·문구·원본 관계가 겹치면 독립성을 확보한 것이 아니다.

### 엄격한 분리를 위한 방법 — 아직 시행하지 않은 제안

1. 원문과 모든 파생 fixture·가시 대조군을 원본 관계로 연결한다. 동일 문구, 광고 목적지, 브랜드 및 의심 캠페인 관계도 함께 기록한다.
2. 출처 사이트 계열을 기본 그룹으로 만들고, 동일 캠페인 또는 원문/파생 관계로 연결된 그룹을 하나로 합친다. 같은 그룹은 train·validation·test 중 한 곳에만 배정한다.
3. 그룹 단위로 유형과 현재/과거 근거 비율을 최대한 고려해 분할한다. 80/20 같은 비율은 목표로만 사용하고 그룹을 쪼개 비율을 맞추지 않는다. 14개 출처 계열만으로 모든 유형의 독립 test를 확보하기 어려우면 신규 사이트에서 추가 수집한다.
4. sample_id, original_id, source_family, campaign_group, split과 분할 규칙·seed를 manifest에 기록한다. 선택한 test는 모델이나 규칙을 조정하는 데 사용하지 않는다.
5. 분할 간 출처 계열, 캠페인, 원본/파생 연결이 겹치지 않는지 검사하고 동일·유사 문구와 HTML/CSS 템플릿의 중복도 점검한다. 동일 CSS 기법 자체는 평가 목적상 공유될 수 있지만 특정 템플릿 암기로 성능이 부풀려지지 않도록 확인한다.
6. test의 유형별·출처별 성능과 오탐률을 따로 보고한다. 정상 접근성·UI 사례 등 실제 음성 데이터도 독립 출처에서 확보한다.

## 7. 부족 데이터와 생성 아이디어

| 부족 부분 | 생성 아이디어 | 이번 적용 |
|---|---|---|
| 공공서비스 문맥 | 민원·공지·입찰·복지의 가상 페이지에 문맥과 무관한 외부 홍보 배치 | 4개 문맥 |
| 정상 숨김 UI | 동일 CSS에 정상 경고·도움말을 적용하여 광고와 짝지음 | 정상 숨김 28개 |
| 키워드에 의존하는 오탐 | 정상 경고문에 광고와 같은 문구를 인용 | 모든 정상 숨김 사례에 적용 |
| CSS만 보고 판단하는 오탐 | 가시 광고와 CSS 복원 광고를 음성으로 추가 | 각 28개 |

다음 확장 아이디어는 시간에 따라 열리는 탭, 모바일에서만 숨김, 상위 요소 숨김과 자손 복원, 정상 접근성 링크의 focus 표시, 이미지와 텍스트의 같은 광고 중복이다. 이번 112개에는 구현하지 않았다. 동적 상태 사례는 상태 전후를 별도 기록하고 실브라우저 검증을 확보한 후 추가하는 것이 적절하다.

## 8. 추가 합성 데이터의 생성 기준과 결과

생성식은 **4개 문맥 × 7개 기법 × 4개 역할 = 112개**다. 사람3 담당 OFFSCREEN 범위 안에서 직접 작성했으며, 기존 원문의 광고 문구나 목적지를 복사하지 않았다.

기법은 font-size:0, 음수 left, display:none, visibility:hidden, clip-path, 음수 text-indent, transform이다. 민원 우선 처리 유료 대행·외부 베팅 혜택·입찰 선정 보장·지원금 전 선입금이라는 가상 홍보를 문맥별로 작성했다. 법적 불법 여부를 판정한 데이터가 아니라 해당 주제의 탐지 상황을 모사하는 자료다.

| 역할 | 수량 | OFFSCREEN 탐지 라벨 | 이유 |
|---|---:|---|---|
| hidden_promotion | 28 | 양성 | 문맥과 무관한 외부 홍보를 숨김 |
| legitimate_hidden_ui | 28 | 음성 | 기관 경고·도움말의 숨김 표시 상태; 광고 문구를 인용해도 홍보하지 않음 |
| visible_promotion | 28 | 음성 | 외부 홍보는 있으나 가시 상태이므로 OFFSCREEN 양성 아님 |
| restored_promotion | 28 | 음성 | 숨김 선언은 있지만 후속 CSS가 표시 상태로 복원 |

`is_positive`는 **숨김 홍보 탐지** 라벨이다. 전체 불법 광고 탐지 라벨과 같지 않다. 가시 홍보 음성을 전체 광고 탐지기의 음성으로 그대로 사용하면 잘못된 학습이 된다. `promotion_present`와 `expected_hidden`을 함께 제공하고, `legal_status=not_determined`를 유지했다. 숨김 정상 UI는 상태를 모사한 음성 사례이며 모든 CSS 방식이 접근성에 적합한 구현이라는 뜻은 아니다.

중립적인 후보 요소 ID를 모든 역할에 동일하게 사용하고 한 묶음의 광고는 같은 문구·목적지를 공유한다. 역할 이름·라벨·합성 표시·split은 모델 입력에서 제외한다. 연결 주소는 `service.example`의 가상 경로이고, 외부 라이브러리·이미지·JavaScript 없이 HTML/CSS로 동작한다. 실제 기관 이름·로고·계정은 사용하지 않았다.

## 9. 추가 합성 데이터의 분할과 검증 범위

민원·공지·입찰 84개는 학습 보강용, 복지 28개는 합성 validation용으로 배정했다. 같은 문맥의 모든 기법·역할을 한쪽에 묶었으므로 원본/대조군이 양쪽으로 분산되지 않는다. **실제 test 데이터는 이번 생성물에 없다.** 공통 생성기가 남아 있으므로 validation은 생성 템플릿 내 점검이며 실제 사이트 일반화의 증거로 사용하지 않는다.

112개 ID의 고유성, 파일별 SHA256, 후보 요소 구조, 역할과 라벨의 일치, 문맥 그룹의 분할 간 중복 0개를 정적으로 검증했다. 브라우저 자동화 도구가 현재 환경에 없어 실제 렌더링은 실행하지 않았으며 모든 데이터에 `rendering_verified=false`를 기록했다. '숨겨짐'은 작성 의도이고 사람이 화면 검수로 확정해야 한다.

검수는 최소한 데스크톱·모바일에서 양성/정상 숨김이 읽히지 않는지, 가시/복원 사례가 읽히는지, CSS를 제거하면 모든 문구가 나타나는지 확인해야 한다. 정상 UI에서 가시성 외에 역할·문맥·링크 유무도 확인한다. 검수 후 결과를 별도 기록하고 원본 생성 데이터의 기대값과 관찰값을 구분한다.
