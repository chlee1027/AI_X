## 2. 데이터를 어떻게 생각했나 (설계 원칙)

1. **테스트셋은 실제 수집만 쓴다.** 탐지기와 생성 데이터를 같은 사람(같은 모델)이 만들면, 탐지기가 잡기 쉬운 모양으로 데이터가 만들어진다. 대회가 재려는 것은 "실제 공공 사이트에서 잡히는가"이므로, 테스트셋에는 실제 페이지에서 나온 마크업만 넣었다. 생성 데이터가 필요하면 나중에 실제 데이터를 보지 않고 따로 만들어 따로 보고한다.
2. **정답 단위를 채점 단위에 맞춘다.** 샘플 하나 = 요소 하나 = 선택자 하나. 문장 단위나 페이지 단위로 모으지 않았다.
3. **분포를 억지로 맞추지 않는다.** 계획서 쿼터(전각 30, 키릴·그리스 25 …)는 목표였지만, 실제 분포가 다르다는 것 자체가 발견이다. 쿼터를 맞추려고 데이터를 버리거나 만들지 않았다.
4. **눈으로 안 보이는지는 브라우저로 확인한다(TR).** HTML 문자열만 보면 정상 애니메이션의 `opacity:0`까지 잡힌다. 실제 Edge로 그려서 계산된 스타일로 확정했고, 숨김 스타일이 인라인으로 직접 걸린 것만 넣었다.
5. **반복은 상한으로 줄인다.** 한 캠페인이 제목만 바꿔 수백 번 올린 글이 많다. 전체판은 그대로 두고, 평가용 권장판에만 상한을 걸었다.
6. **수집 규칙을 지킨다.** robots.txt 준수, 요청 간격 1.2~1.5초, 403/429·robots 차단은 우회하지 않음, 광고가 가리키는 불법 사이트에는 접속하지 않음, 휴대폰 번호는 위장 모양을 유지한 0으로 가림.

## 4. 왜 이만큼 모았나 (수집량 근거)

### 4-1. 새로 나오는 것이 거의 없어질 때까지 모았다 (포화)

생태학에서 표본으로 전체 종 수를 추정하는 방법(Good's coverage, Chao1)을 캠페인·사이트에 썼다. "다음에 하나 더 모으면 처음 보는 캠페인일 확률"이 Good's coverage의 반대값이다.

| 지표 | 값 | 뜻 |
|---|---:|---|
| HG 전체판 캠페인 수(관측) | 128 | |
| HG Good's coverage | **97.5%** | 다음 샘플이 새 캠페인일 확률 2.5% |
| HG Chao1 추정 캠페인 수 | 178.6 | 관측 128은 추정치의 72% |
| HG 누적 곡선(무작위 순서 200회 평균) | 50% 지점 98.5개 → 90% 지점 123.5개 → 100% 128개 | 마지막 10% 샘플에서 새 캠페인 4.5개만 추가 |
| TR 사이트 Chao1 | 관측 26 / 추정 34.0 | 관측은 추정치의 76% |
| TR 수집 속도(10-08 밤) | 1시간에 새 사이트 약 1곳 | 이 시점에 수집을 멈춤 |

Chao1 추정치와 관측치의 차이(HG 약 50개 캠페인, TR 약 8개 사이트)는 "아직 못 찾은 것"의 크기다. 국내 HG에서는 이 차이의 상당 부분이 **이미 삭제된 게시판**이다(키릴 도메인 비아그라 캠페인이 bufs·hanseo·snu 등 여러 대학 게시판에 있었지만 게시판이 삭제되어 검색 색인만 남음).

### 4-2. 평가 숫자를 믿을 수 있을 만큼 모았다 (통계적 정밀도)

| 데이터 | 건수 | 재현율 90%일 때 95% 신뢰구간 | 재현율 80%일 때 |
|---|---:|---:|---:|
| HG 권장판 | 372 | ±3.0%p | ±4.1%p |
| TR 권장판 | 232 | ±3.9%p | ±5.1%p |

±5%p 안쪽이면 "규칙 하나를 바꿨더니 재현율이 올랐다"를 구분할 수 있다. 같은 기준을 100건짜리 카테고리에 쓰면 ±5.9%p다.

### 4-3. 전체판을 그대로 쓰지 않고 상한을 건 이유

HG 전체판 1,777건은 상위 2개 사이트(counselpsy.hannam.ac.kr 837, ypcd.or.kr 478)가 74%다. 같은 캠페인이 제목만 바꿔 반복된 것이라, 그대로 쓰면 탐지기가 그 캠페인 하나만 잡아도 점수가 크게 오른다. 캠페인당 5건(HG), 사이트당 20건(TR) 상한을 건 권장판을 기본 테스트셋으로 했다.

## 5. 이 데이터의 특별함

### 5-1. 실제 공격 분포가 계획서 예상과 다르다

| HG 하위 유형 | 계획서 쿼터(100 기준) | 권장판 실측(372) | 비율 |
|---|---:|---:|---:|
| digit_letter(숫자↔문자, `OlO`·`ㅇ1ㅇ`) | 20 | 103 | 27.7% |
| enclosed_alnum(원문자·수학 영숫자 `ⓓⓒⓚ`·`𝐀𝐧𝐲`) | (없음) | 75 | 20.2% |
| fullwidth(전각 `ｈｏｎｇｂｏ`) | 30 | 50 | 13.4% |
| hangul_lookalike(`ㅋr톡`) | (없음) | 47 | 12.6% |
| fullwidth_symbol(점 위장 `님。com`) | 10 | 45 | 12.1% |
| partial_token(단어 일부 치환) | 15 | 34 | 9.1% |
| cyrillic_greek(`нσиgвσ`, `.cом`) | 25 | 18 | 4.8% |

- 계획서가 가장 많을 것으로 본 키릴·그리스(25)는 실제로 가장 적다(4.8%). 실제 주류는 연락처 숫자↔문자 치환과 원문자·수학 영숫자다.
- 위장은 **연락처와 도메인**에 몰려 있다. 본문 SEO 낱말("출장마사지", "카지노")은 대체로 위장하지 않는다. 탐지기는 문장 전체가 아니라 연락처·도메인 토큰을 집중해서 봐야 한다.

| TR 하위 유형 | 요강 문구 | 권장판(232) |
|---|---|---:|
| opacity_zero | opacity:0 | 110 |
| color_matches_bg | 배경색과 동일한 색상 | 88 |
| color_alpha_zero | color:transparent | 34 |
| text_fill_color / bg_image | (계획서 하위 유형) | 0 |

## 8. 이 데이터를 실제 테스트에 어떻게 넣을까

### 8-1. 다섯 단계 시험

주최 측 적격평가는 "URL 하나를 넣으면 크롤링부터 result.json까지"다. 그래서 조각 단위 정확도만 보면 안 되고, 실제 적격평가 흐름과 같은 시험이 필요하다. 다섯 단계로 나눈다.

| 단계 | 이름 | 입력 | 재는 것 | 데이터 성격 |
|---|---|---|---|---|
| T1 | 조각 시험 | YAML의 `html`+`css` 조각 | 탐지 함수가 정답 요소를 맞히는지(재현율) | 실데이터 그대로 |
| T2 | 난이도 가중 시험 | T1 결과 + 샘플별 가중치 | 어려운 샘플을 얼마나 잡는지 | 실데이터 그대로 |
| T3 | 재배치 시험 | 실제 문구·마크업을 국내 공공 사이트형 모의 사이트의 게시글·댓글·iframe·목록 위치에 넣음 | 크롤러 + 탐지 + result.json 전체. 요강 채점 규칙 그대로 | **배치는 인공**(별도 표기) |
| T4 | 함정 시험 | 음성 후보 + 근접 오답 + 그라데이션 글자 | 오탐률(정확도 35점 대응) | 실데이터 그대로 |
| T5 | 시간 시험 | 실제 감염 게시판 규모(목록 수천 쪽)를 흉내 낸 모의 사이트 | 30분 안에 끝나는지, 시간 대비 정답 수 | 배치는 인공(별도 표기) |

T3·T5는 실제 문구를 쓰지만 위치는 우리가 정한 것이므로 실데이터 성적과 섞지 않고 따로 보고한다.

### 8-2. 점수를 매기는 방식 (창의적 평가 설계)

**(1) 난이도 가중 재현율(DW-Recall)**

샘플 i의 가중치 = 1 + 난이도 점수(5-3절). 재현율 = Σ(가중치 × 맞힘) / Σ가중치.

- HG 권장판 가중치 합 1,249, TR 권장판 507.
- 예: HG에서 NFKC 비교만 하는 탐지기가 R=0(91건)만 맞히면 단순 재현율은 24.5%지만, 이 샘플들의 가중치 합은 241이라 DW-Recall은 19.3%(241/1,249)로 내려간다. 어려운 것을 잡을수록 두 값의 차이가 커진다.
- 단순 재현율과 DW-Recall을 같이 보고한다. 둘의 차이가 크면 "쉬운 것만 잡는 탐지기"다.

**(2) 사이트 복잡도 가중(T3 재배치 시험)**

같은 광고라도 사이트가 복잡하면 찾기 어렵다. 모의 사이트에 복잡도 점수를 매기고, 정답 1건의 점수에 더한다.

| 요소 | +1 조건 | 근거(실데이터에서 본 것) |
|---|---|---|
| 탐색 깊이 | 진입 URL에서 3클릭 이상(목록 → 게시글 → 댓글) | 실제 스팸 대부분이 게시글·목록 깊은 쪽에 있음 |
| 쿼리 페이지 | `view?id=` 처럼 쿼리로만 구분 | 검색결과 반사 19건, 요강 12쪽 |
| iframe | iframe 안(중첩이면 겹마다 +1) | 요강 5·11쪽 |
| JS 렌더링 | 목록이 JS로 그려짐 | 게시판 순회 때 JS 목록 때문에 0건이던 곳이 많았음 |
| DOM 깊이 | 정답 요소 깊이 12단계 이상 | TR 원본 중앙값 7, 최대 17 |
| 클로킹 | 자동화 UA에는 다른 내용을 보여 줌 | javeriana.edu.co 실제 사례 |

**(3) 요강 그대로의 모의 채점기**

T3·T5 결과(result.json)를 요강 12쪽 규칙 그대로 채점한다.
- URL 비교: 끝 `/`, http/https, `#` 이하는 무시. 쿼리 순서만 다르면 같은 페이지, 쿼리 값이 다르면 다른 페이지
- location: 문자열이 아니라 "같은 요소를 가리키는가"로 비교(모의 사이트 DOM에서 선택자를 실제로 실행)
- 선택자가 2개 이상 요소를 가리키면 오답
- url·location·technique가 같은 중복은 1건
- 정답 검출 개수(45) · 정확도(35) · 시간(20, 30분 상한)으로 환산한 **예상 적격평가 점수**를 낸다

**(4) 일반화 점수: 사이트 단위 교차 검증**

규칙을 맞출 때 쓴 사이트와 시험하는 사이트를 나눈다. 사이트를 하나씩 빼고 나머지로 규칙을 정한 뒤, 뺀 사이트에서 잰다(leave-one-site-out). TR은 26곳이라 26번, HG는 18곳이라 18번. 이 값과 전체 재현율의 차이가 "사이트를 외운 정도"다.

**(5) 성적표 한 장**

### 8-3. 데이터 분할

- 사람 2 데이터는 전부 `split: test`다. 탐지 규칙을 맞추는 데 test를 쓰지 않는다.
- 규칙 개발은 **사이트 단위로 나눈 개발용 묶음**에서만 한다. 전체판에서 권장판을 뺀 나머지(HG 1,405, TR 309)는 같은 캠페인·사이트의 반복이라 개발용으로 쓰면 test와 거의 같은 것을 보고 맞추는 셈이 된다. 그래서 이 나머지는 "같은 캠페인 반복에서 결과가 흔들리지 않는가" 확인용으로만 쓴다.
- 최종 test(권장판 전체)는 마지막에 한 번만 돌린다.
